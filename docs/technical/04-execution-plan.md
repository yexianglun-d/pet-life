# 宠物生活管家技术实施计划

## 1. 规划前提

### 1.1 输入文档

- 产品总览：`docs/product/01-product-overview.md`
- 信息架构：`docs/product/02-information-architecture.md`
- 页面级 PRD：`docs/product/03-prd-core-pages.md`
- 产品层业务实体模型：`docs/product/05-business-entities.md`
- 技术设计：`docs/technical/01-system-design.md`
- API 契约：`docs/technical/02-api-and-events.md`
- DDL 草案：`docs/technical/03-ddl-draft.sql`

### 1.2 规划目标

将现有技术方案转化为：

1. 可按依赖顺序执行的建设主线
2. 可验证的阶段任务
3. 可落地的验收标准
4. 可直接跟进的测试与发布检查点

### 1.3 规划原则

1. 先打通 `登录 -> 建宠 -> 记录 -> 时间轴 -> 首页` 主链路。
2. 先做单一事实源和权限骨架，再做高层页面和内容分发。
3. 风险型外部依赖前置验证，但仅验证当前批次必需集成。
4. 商城与设备仅保留用户端占位和技术预留，不进入当前实施批次。

## 2. 建设策略

## 2.1 Build Spine

最小建设主线如下：

`基础设施 -> 认证/宠物主档 -> 媒体上传 -> 健康/日常记录 -> 时间轴/首页 -> 社区 -> 服务预约 -> 家庭共养 -> 发布加固`

### 2.2 为什么这样排

1. 没有账号、宠物和媒体链路，后面所有能力都无法落地。
2. 健康记录、萌宠日常、时间轴是产品最核心留存路径，必须先打通。
3. 社区和服务都依赖宠物对象、媒体、审核和基础权限。
4. 家庭共养是跨域能力，放在主链路稳定后接入更稳。
5. 商城与设备当前只做占位和预留，不排入实施主线。

## 2.3 阶段划分

| 阶段 | 目标 | 主要输出 | 退出检查点 |
|---|---|---|---|
| Phase 0 | 打基础并前置关键依赖验证 | 工程骨架、环境、迁移框架、上传/审核可行性验证 | 开发环境可跑、基础依赖可联通 |
| Phase 1 | 打通用户和宠物主链路入口 | 登录、当前宠物、宠物 CRUD、媒体资产基础能力、首页最小聚合 | 用户可登录并创建宠物进入首页 |
| Phase 2 | 打通核心价值闭环 | 健康记录、提醒、萌宠日常、时间轴、通知中心 | 用户可完成记录并在首页/时间轴回看 |
| Phase 3 | 建立增长闭环 | 社区发帖、评论、点赞、收藏、审核、举报 | 公开内容能审核后进入社区流 |
| Phase 4 | 建立本地服务能力 | 服务商目录、医院/服务预约、预约记录、评价骨架 | 用户可从服务页发起并回看预约 |
| Phase 5 | 完成协同与发布准备 | 家庭邀请、角色权限、共享宠物、占位页校准、全链路加固、发布检查 | 用户端主链路可回归验证并具备上线条件 |

## 3. 阶段任务拆解

## 3.1 Phase 0：基础设施与风险前置

### 阶段目标

建立统一工程底座，并尽早验证会阻塞后续研发的外部依赖。

| 任务 | 主要输出 | 依赖 | 完成标准 | 验证方式 |
|---|---|---|---|---|
| 0.1 工程骨架初始化 | Flutter App、后台管理、Spring Boot 服务端骨架；统一配置、日志、环境变量模板 | 无 | 三端工程可启动，基础目录与模块结构稳定 | 本地启动、CI 构建通过 |
| 0.2 数据库迁移框架接入 | Flyway/Liquibase、基础库连接、首批迁移目录规范 | 0.1 | 能执行空迁移和初始化迁移 | 迁移命令执行成功，数据库版本表生成 |
| 0.3 公共能力基线 | 统一响应格式、错误码、鉴权拦截器、权限中间件、审计基类、outbox 基类 | 0.1 | 业务模块可以直接复用公共组件 | 接口单测、基础冒烟接口返回规范化结果 |
| 0.4 外部依赖验证 Spike | 短信、OSS、CDN、内容审核、地图接入方式验证 | 0.1 | 每项能力都形成接入结论与 demo 结果 | 接入记录、demo 截图、结论文档 |
| 0.5 可观测性基线 | trace id、访问日志、错误日志、慢 SQL 记录、基础指标埋点 | 0.1 | 基础问题可定位，不依赖人工猜测 | 日志输出、监控面板样例 |

### 阶段验收标准

1. 后端服务、移动端壳、后台壳均可正常启动。
2. 数据库迁移框架可管理版本。
3. 鉴权、统一错误码、日志、审计、outbox 基座可复用。
4. 外部依赖已明确可行方案和风险，不留纯猜测。

### 阶段测试

- 单元测试：错误码、配置加载、权限中间件基础逻辑。
- 集成测试：数据库连接、迁移执行、对象存储上传签名。
- 手工验证：短信、审核、地图接入 PoC。

## 3.2 Phase 1：用户与宠物主链路

### 阶段目标

让用户可以登录、建宠、切换当前宠物，并进入最小可用首页。

| 任务 | 主要输出 | 依赖 | 完成标准 | 验证方式 |
|---|---|---|---|---|
| 1.1 登录与会话管理 | 短信登录、token 刷新、用户信息接口、用户设置表落地 | Phase 0 | 用户可登录、刷新 token、获取 `me` 信息 | 接口集成测试、登录手工冒烟 |
| 1.2 宠物与家庭基础模型 | 宠物创建/编辑/详情/列表；家庭初始化骨架；当前宠物切换 | 1.1 | 用户可创建多只宠物并切换当前宠物 | API 测试、移动端流程走查 |
| 1.3 媒体资产最小链路 | 上传凭证、直传、上传完成确认、头像/宠物图片使用 | 1.1、0.4 | 媒体可安全上传并回填业务 | 集成测试、图片上传手工验证 |
| 1.4 首页最小聚合 | 当前宠物卡、宠物摘要、空状态引导、消息数占位 | 1.2、1.3 | 登录后可进入首页且显示正确宠物上下文 | 首页接口响应测试、页面冒烟 |
| 1.5 基础权限校验 | 宠物归属校验、当前宠物越权保护、审计日志最小链路 | 1.2、0.3 | 非拥有者不可访问他人宠物数据 | 权限集成测试、异常场景回归 |

### 阶段验收标准

1. 用户可完成 `登录 -> 创建宠物 -> 进入首页`。
2. 多宠切换后首页上下文正确变化。
3. 图片上传、头像设置、宠物头像展示链路正常。
4. 越权访问宠物接口会返回明确错误码。

### 阶段测试

- 单元测试：登录态解析、当前宠物切换、权限判断。
- 集成测试：登录、创建宠物、上传媒体、首页聚合。
- E2E：登录 -> 建宠 -> 上传头像 -> 进入首页。
- 手工 QA：短信频控、异常 token、无宠物空状态。

## 3.3 Phase 2：核心价值闭环

### 阶段目标

打通健康记录、萌宠日常、提醒、时间轴、通知这条留存主链。

| 任务 | 主要输出 | 依赖 | 完成标准 | 验证方式 |
|---|---|---|---|---|
| 2.1 健康记录能力 | 疫苗/驱虫/体检/用药/异常观察 CRUD | Phase 1 | 记录可写入、查询、回显，字段语义正确 | API 集成测试、表单流程测试 |
| 2.2 提醒状态机 | 创建提醒、完成提醒、跳过提醒、自动生成下一次提醒 | 2.1 | 提醒状态只能按规则流转 | 单元测试、状态流转集成测试 |
| 2.3 萌宠日常链路 | 新建日常、列表、详情、可见性控制 | 1.3、1.5 | 用户可 3 步内完成日常记录 | E2E、列表/详情接口测试 |
| 2.4 时间轴派生 | `pet_timeline_events`、outbox worker、补偿任务 | 2.1、2.3、0.3 | 健康记录和日常都能派生到时间轴 | worker 集成测试、补偿任务验证 |
| 2.5 通知中心基础 | 提醒通知、系统通知、消息列表、已读状态 | 2.2、2.4 | 关键动作会生成对应通知 | API 测试、手工消息验证 |
| 2.6 首页正式聚合 v1 | 今日待办、最近日常、时间轴摘要、通知角标 | 2.2、2.3、2.4、2.5 | 首页完成主价值聚合 | 首页接口压测、页面回归 |

### 阶段验收标准

1. 用户可完成 `记录健康/记录日常 -> 首页回看 -> 时间轴回看 -> 通知收到提醒`。
2. 提醒完成后可按规则生成下一次提醒。
3. 时间轴只读聚合稳定，不反写源数据。
4. 首页聚合结果与事实源一致，缓存不会读出旧宠物上下文。

### 阶段测试

- 单元测试：提醒状态机、时间轴事件映射、可见性判断。
- 集成测试：健康记录创建、日常创建、outbox 消费、通知生成。
- E2E：记一条日常 -> 首页可见 -> 时间轴可见。
- 手工 QA：异常观察、不同可见性、重复点击提交。

## 3.4 Phase 3：社区与审核

### 阶段目标

建立增长闭环，让公开内容可审核、可分发、可互动、可举报。

| 任务 | 主要输出 | 依赖 | 完成标准 | 验证方式 |
|---|---|---|---|---|
| 3.1 社区基础内容模型 | 话题、帖子、评论、点赞、收藏、关注关系 | Phase 2 | 可创建和查询社区核心内容对象 | API 测试、数据校验 |
| 3.2 日常同步社区 | 萌宠日常一键发布、来源记录关联、可见性映射 | 2.3、3.1 | 日常可一键转社区且保留来源关系 | E2E、数据关联验证 |
| 3.3 审核链路 | 文本同步审核、图片视频异步审核、审核状态回写 | 0.4、3.1 | 审核中内容不会进入公开流 | 审核模拟测试、状态回归 |
| 3.4 社区流与详情页 | 推荐/关注/同城/问答基础流，帖子详情、互动计数 | 3.1、3.3 | 审核通过内容可进入流和详情页 | 列表分页测试、详情回归 |
| 3.5 举报与后台处理骨架 | 举报、状态处理、后台审核入口、审计日志 | 3.1、0.3 | 举报可形成待处理记录并可被处理 | 后台流程手工验证 |

### 阶段验收标准

1. 用户可从日常一键发布公开内容。
2. 审核中和拒绝内容不会进入公开流。
3. 评论、点赞、收藏、举报均可闭环。
4. 社区帖子删除不会删除原始日常记录。

### 阶段测试

- 单元测试：帖子权限、审核状态迁移、互动计数逻辑。
- 集成测试：帖子发布、审核回写、评论互动、举报。
- E2E：日常公开 -> 审核通过 -> 社区可见 -> 互动。
- 手工 QA：审核中展示、举报入口、同城切换。

## 3.5 Phase 4：服务目录与预约

### 阶段目标

让用户能够浏览服务商并完成医院/寄养/洗护/训练预约。

| 任务 | 主要输出 | 依赖 | 完成标准 | 验证方式 |
|---|---|---|---|---|
| 4.1 服务商基础数据 | 服务商、服务项目、城市开通状态、后台维护入口 | Phase 1 | 可按城市和类型查询服务商 | API 测试、后台录入验证 |
| 4.2 预约时段能力 | 时段表、时段查询、可预约名额控制 | 4.1 | 同一时段不会超卖 | 并发集成测试 |
| 4.3 预约创建与取消 | 医院/服务预约创建、取消、记录列表 | 4.1、4.2、1.5 | 用户可发起预约并回看状态 | E2E、状态流转测试 |
| 4.4 预约联动时间轴/通知 | 预约成功后进入时间轴与通知中心 | 4.3、2.4、2.5 | 预约后用户能收到通知并在宠物视图回看 | 集成测试 |
| 4.5 服务评价骨架 | 服务评价、评分回写、评价列表 | 4.3 | 已完成预约可评价 | API 测试、后台核对 |

### 阶段验收标准

1. 用户可浏览服务商、进入详情、发起预约、取消预约、查看记录。
2. 不可预约城市返回预留态数据，而不是空白。
3. 预约创建具备时段和权限校验。
4. 预约记录能够回写宠物视图。

### 阶段测试

- 单元测试：时段可预约性、预约状态机。
- 集成测试：服务商查询、时段锁定、预约创建/取消。
- E2E：服务详情 -> 预约 -> 消息通知 -> 记录页可见。
- 手工 QA：未开通城市、医院详情电话/导航、重复提交预约。

## 3.6 Phase 5：家庭共养与发布准备

### 阶段目标

完成多人协同、占位页校准和上线准备，让用户端主链路达到可发布状态。

| 任务 | 主要输出 | 依赖 | 完成标准 | 验证方式 |
|---|---|---|---|---|
| 5.1 家庭邀请与共享宠物 | 邀请、接受、角色、共享宠物选择 | Phase 1、1.5 | 家庭成员关系可建立，角色生效 | API 测试、邀请流程手工验证 |
| 5.2 共享权限扩展 | 共享宠物查看、记录、提醒处理、敏感操作拦截 | 5.1、Phase 2 | owner/admin/member 权限差异正确 | 权限矩阵集成测试 |
| 5.3 占位页与预留能力校准 | 商城真实占位页、设备预留页、未开通能力配置化返回 | Phase 1、Phase 4 | 用户端预留页口径统一，不触发不存在接口 | UI 联调、空态回归 |
| 5.4 全链路回归与性能基线 | 核心流程回归、首页/社区/时间轴/预约压测、监控告警校准 | 全阶段 | 用户端主链路稳定，无阻断性缺陷 | 压测报告、回归清单 |
| 5.5 发布准备 | 灰度策略、配置检查、应急预案、数据初始化脚本 | 5.4 | 达到上线门槛，可灰度发布 | 发布清单审阅 |

### 阶段验收标准

1. 家庭成员可按角色共享宠物并执行被授权操作。
2. 敏感操作必须在服务端拦截未授权成员。
3. 商城和设备页面均以预留态返回，不调用未实现后端链路。
4. 用户端主链路完成一轮全量回归并具备上线条件。

### 阶段测试

- 单元测试：角色权限矩阵、预留态配置解析、占位页状态映射。
- 集成测试：邀请接受、共享宠物权限、预留态接口返回。
- E2E：邀请成员 -> 共享宠物 -> 成员查看待办；进入商城占位页/设备预留页 -> 返回预留说明。
- 手工 QA：多成员切换、邀请失效、预留页文案与入口一致性。

## 4. 依赖关系与并行策略

## 4.1 强依赖链

1. `Phase 0 -> Phase 1 -> Phase 2` 是绝对主干，不能跳过。
2. 社区依赖媒体上传、宠物对象、审核与时间轴基础，因此必须晚于 Phase 2。
3. 服务预约依赖账号、宠物、通知和权限，因此必须晚于 Phase 1，并建议晚于 Phase 2。
4. 家庭共养依赖成熟的宠物权限模型，因此放在主路径稳定后。
5. 商城和设备不进入当前批次，只保留用户端占位与技术预留。

## 4.2 可并行任务

1. `后台管理壳` 可从 Phase 0 并行启动。
2. `服务商后台录入` 可在 Phase 3 期间并行建设，为 Phase 4 提前铺数据。
3. `举报处理后台入口` 可在 Phase 3 期间并行建设。
4. `商城占位页` 与 `设备预留页` 可在 Phase 4 后期并行联调，为 Phase 5 做收口。

## 4.3 外部等待项

1. 短信服务商备案和发送模板审核。
2. 内容审核服务商账号开通。
3. 地图服务 key 与配额。
4. 服务商基础数据来源和初始化方式。
5. 后台账号体系与权限模型。

## 5. DDL 与迁移批次建议

不要一次把全部 DDL 同步进首个迁移版本，应按阶段分批落库。

| 迁移批次 | 建议表范围 | 对应阶段 |
|---|---|---|
| M1 | `users`、`user_settings`、`user_sessions`、`families`、`family_members`、`family_invitations`、`pets`、`media_assets`、`audit_logs` | Phase 0-1 |
| M2 | `pet_health_records`、`pet_reminders`、`pet_daily_logs`、`pet_timeline_events`、`notifications`、`message_templates`、`outbox_events` | Phase 2 |
| M3 | `community_topics`、`community_posts`、`community_comments`、`community_post_reactions`、`community_post_favorites`、`community_reports`、`user_follows`、`moderation_tasks` | Phase 3 |
| M4 | `service_providers`、`provider_service_items`、`provider_schedule_slots`、`service_appointments`、`provider_reviews` | Phase 4 |

说明：

- `products/*` 与 `devices/*` 相关表保留在全量 DDL 草案中，但不进入当前迁移计划。

## 6.3 E2E 重点场景

1. 登录 -> 建宠 -> 首页
2. 记录日常 -> 首页 -> 时间轴
3. 创建健康记录 -> 生成提醒 -> 完成提醒
4. 日常公开 -> 审核通过 -> 社区可见 -> 互动
5. 服务详情 -> 预约 -> 通知 -> 记录页
6. 邀请家庭成员 -> 共享宠物 -> 成员处理待办
7. 首页/服务页 -> 商城占位页或设备预留页 -> 预留态说明

## 6.4 手工 QA 重点

- 空状态和未开通城市
- 登录限流和验证码异常
- 媒体上传失败重试
- 多宠切换与上下文正确性
- 审核中内容展示
- 权限边界和越权提示
- 预留页文案、入口、返回行为一致性

## 8. 发布前检查清单

1. 所有数据库迁移脚本可从空库完整执行。
2. 核心配置项分环境校验通过。
3. 关键错误码和日志字段在生产环境可观测。
4. OSS、短信、审核、地图相关配置和白名单校验完成。
5. 首页、记录、社区、预约、家庭共养、预留页链路至少完成一轮全量回归。
6. 敏感操作全部有服务端鉴权和审计。
7. 回滚方案与数据补偿脚本已准备。

## 9. 风险与开放项

## 9.1 主要风险

1. 审核服务响应和策略可能影响社区发布时间和用户体验。
2. 预约时段和服务商目录若缺少初始化数据，会导致功能存在但不可用。
3. 家庭共养一旦权限模型定义模糊，后期返工成本高。
4. 商城和设备如果预留页口径不统一，会引发用户误解和研发误开工。

## 9.2 对应处理

1. 审核链路保持 `pending_review` 安全默认态，不因为超时放行。
2. 服务目录和时段后台应提前并行建设。
3. 商城与设备统一采用配置化预留态，避免半成品接口外露。
4. Phase 1 就先建立宠物权限守卫，Phase 5 再补完整家庭协同。

## 9.3 当前仍需明确的事项

1. 商城占位页放首页、服务页还是仅保留二级入口。
2. 设备预留页是否对用户展示开放计划和订阅入口。
3. 后台是否使用独立账号体系还是复用用户体系扩展角色。
4. 社区推荐流首期是纯规则流还是需要简单打分策略。
